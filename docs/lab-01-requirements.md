## Предметная область

Заказчик — отдел информационной безопасности ООО «Софт решения». Ведём процесс учёта сервисных учётных записей Active Directory, оценки связанных с ними рисков ИБ и контроля устранения выявленных нарушений. Сейчас учётные записи живут в Excel-таблицах и переписке с администраторами, поэтому единая запись в системе заменяет разрозненные таблицы, чаты и устные договорённости: в любой момент видно, какие учётные записи существуют, кто за них отвечает, какие риски по ним выявлены и на каком этапе устранение.

## Как есть

1. Сервисные учётные записи заводятся системными администраторами по мере необходимости и нигде централизованно не регистрируются.
2. Список учётных записей ведётся в Excel-таблице, которая расходится по почте и устаревает через неделю.
3. При увольнении владельца учётной записи информация о ней теряется, и учётка остаётся «ничейной» с активным паролем.
4. Отдел ИБ узнаёт о проблемных учётных записях только по факту инцидента или во время аудита.
5. Пароли сервисных учёток часто не меняются годами, но это выясняется только вручную при проверке.
6. Нет единого реестра рисков: каждый аналитик ведёт свой список в блокноте.
7. Через месяц невозможно понять, кто и какую задачу по устранению риска должен был выполнить.
8. Задачи по устранению нарушений ставятся в мессенджере и теряются при смене ответственных.
9. Нет сводки по просроченным и закрытым задачам для отчётности перед руководством.
10. Вся работа по контролю сервисных учёток построена на памяти сотрудников и разрозненных файлах.

## Как будет

Одной записью в системе становится задача по устранению риска сервисной учётной записи: машинный `id`, человеческий номер `SAR-2026-NNNN`, заголовок, ссылка на учётную запись (`serviceAccountId`), описание риска, инициатор, назначенный исполнитель, срок, статус и результат. Аналитик ИБ создаёт задачу, координатор отдельным действием назначает системного администратора-исполнителя и ставит срок, системный администратор переводит задачу в `InProgress`, выполняет мероприятия и закрывает её (`Closed`) с фиксацией результата. После любого успешного действия пользователь видит задачу в списке с номером и актуальным статусом.

## Граница

**Внутри семестра (делаем):** главная сущность «задача по устранению риска», справочник сервисных учётных записей (с базовыми атрибутами: SAMAccountName, владелец, связанные системы), назначение исполнителя, смена четырёх статусов, три экрана (список, создание, вход), хранение в PostgreSQL. Интеграционные источники (Active Directory, журналы Windows) заменяются тестовыми данными в БД.

**Снаружи (не делаем в семестре):** реальная интеграция с Active Directory по LDAP/WinRM, отправка уведомлений по Email/Telegram, расчёт риска по сложным формулам с весами, мобильное приложение, модуль аудита (роль «Аудитор» только проектируется), интеграция с Event Viewer Windows.

## Роли

| Роль | Создаёт | Назначает исполнителя | Меняет статус |
|------|---------|------------------------|---------------|
| Аналитик ИБ (инициатор) | да | нет | да (только `Cancelled` у своей записи в статусе `New`, пока не назначен исполнитель) |
| Координатор (назначает, смотрит сводку) | нет | да | нет (может отменить задачу) |
| Системный администратор (исполнитель) | нет | нет | да (только свои: `New`→`InProgress`→`Closed`, либо `InProgress`→`Cancelled`) |

Правило курса: кто создаёт — не тот, кто закрывает чужую запись. Автор задачи не назначается её исполнителем. Исполнитель двигает **только свою**.

## Функциональные требования

- **ФТ-1.** Аналитик ИБ заполняет заголовок (5–80), выбирает сервисную учётную запись из справочника (`serviceAccountId` > 0), описание риска и требуемых мероприятий (10–500) и нажимает «Создать» — видит в списке задачу со статусом «Зарегистрирована» (`New`) и номером SAR-2026-NNNN.
- **ФТ-2.** Аналитик ИБ открывает экран списка и видит только задачи, которые он создал: номер, заголовок, учётную запись, статус, срок.
- **ФТ-3.** Аналитик ИБ отменяет свою задачу в статусе `New` (до назначения исполнителя) отдельной кнопкой «Отменить» — задача получает статус «Отменена» (`Cancelled`).
- **ФТ-4.** Координатор видит список всех задач с фильтрами по статусу и просроченным (сводка).
- **ФТ-5.** Координатор на задаче в статусе `New` отдельным действием «Назначить исполнителя» выбирает системного администратора и устанавливает срок выполнения — исполнитель записан, статус при этом не меняется.
- **ФТ-6.** Системный администратор видит список задач, где он исполнитель, с номерами, сроками и статусами.
- **ФТ-7.** Системный администратор переводит свою задачу `New` → `InProgress` кнопкой «Взять в работу» — статус становится «В работе».
- **ФТ-8.** Системный администратор переводит свою задачу `InProgress` → `Closed` кнопкой «Закрыть», при этом обязательно вводит результат выполнения (текстовое поле) — статус становится «Риск устранён».
- **ФТ-9.** Системный администратор отменяет свою задачу в статусе `InProgress` (ложное срабатывание) — статус становится «Отменена» (`Cancelled`).
- **ФТ-10.** Запрет: системный администратор и координатор не могут создавать задачи; аналитик ИБ не может назначать исполнителя и менять статус чужих задач.
- **ФТ-11.** Запрет: пользователь без входа (не авторизован) не видит список и не может создать задачу — только экран входа.
- **ФТ-12.** Запрет: аналитик ИБ не может быть назначен исполнителем по своей же задаче.

## Нефункциональные требования

- **НФТ-1.** После перезапуска сервера все созданные задачи остаются на месте с теми же номерами и статусами (данные в PostgreSQL).
- **НФТ-2.** Экран списка с 500 задачами загружается не более чем за 2 секунды на учебном ноутбуке.
- **НФТ-3.** Пароли пользователей хранятся только в виде хэша (средствами ASP.NET Core Identity), в логах и ответах API пароль не встречается.
- **НФТ-4.** При ошибке валидации (короткий заголовок, пустое описание) система показывает сообщение у поля и не создаёт задачу.
- **НФТ-5.** Все изменения статусов и назначений логируются (кто, когда, что изменил) в отдельной таблице истории.

## Пользовательские истории (кратко)

- Как аналитик ИБ, хочу создать задачу по устранению риска конкретной сервисной учётной записи, чтобы зафиксировать нарушение в едином реестре.
- Как координатор, хочу назначать исполнителей на поступившие задачи и видеть просроченные, чтобы контролировать устранение рисков.
- Как системный администратор, хочу видеть список назначенных на меня задач с их сроками, чтобы планировать работу и отчитываться о выполненных мероприятиях.

## Обязательные до курсовой (критерии приёмки)

### 1. Создать объект

**Дано:** аналитик ИБ вошёл в систему.  
**Когда:** заполняет заголовок (5–80), ссылку на справочник числом (> 0), описание (10–500) и нажимает «Создать».  
**Тогда:** появляется задача со статусом «Зарегистрирована» (`New`) и человеческим номером SAR-2026-NNNN. Да / нет.

### 2. Назначить исполнителя

**Дано:** координатор вошёл и есть задача в статусе `New`.  
**Когда:** назначает системного администратора отдельным действием (не вместе со статусом).  
**Тогда:** у задачи есть исполнитель; статус ещё можно не менять. Да / нет.

### 3. Исполнитель перевёл в работу

**Дано:** назначенный системный администратор вошёл.  
**Когда:** он переводит свою задачу `New` → `InProgress`.  
**Тогда:** статус «В работе»; чужой логин ту же задачу не двигает. Да / нет.
